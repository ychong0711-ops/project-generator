## 1. CI 워크플로 변경이 푸시되지 않음

### 무슨 일이 있었나

`.github/workflows/ci.yml`에 타입 체크 단계를 추가해서 푸시했으나 GitHub이 거부했습니다.

```
! [remote rejected] arena/01a00b33-project-generator -> arena/01a00b33-project-generator
  (refusing to allow a GitHub App to create or update workflow `.github/workflows/ci.yml`
   without `workflows` permission)
```

Arena가 사용하는 GitHub App 토큰에 `workflows` 스코프가 없어서, 워크플로 파일을 건드리는
푸시는 통째로 거부됩니다. 파일 하나가 아니라 **푸시 전체**가 막히기 때문에, 해당 파일만
원래 상태로 되돌리고(`git checkout 9805c51 -- .github/workflows/ci.yml`) 커밋을 amend 한 뒤
나머지 수정사항을 푸시했습니다.

즉 **CI 파일을 제외한 모든 수정은 정상적으로 올라가 있습니다.**

### 지금 CI는 어떤 상태인가

원격의 `ci.yml`은 초기 커밋 그대로입니다.

```yaml
- name: Install dependencies
  run: npm ci
- name: Run tests
  run: npm test
- name: Build
  run: npm run build
```

여기서 중요한 점은, **`package.json`의 `build` 스크립트를 바꿔뒀다는 것**입니다.

```json
"build": "tsc --noEmit && vite build",
"typecheck": "tsc --noEmit",
```

`build`가 `tsc --noEmit`을 선행하도록 되어 있으므로, **워크플로 파일을 수정하지 않아도
타입 오류는 CI의 Build 단계에서 잡힙니다.** 따라서 이 항목은 "지금 당장 고장난 것"이 아니라
"개선하면 더 좋은 것"에 가깝습니다.

### 굳이 워크플로를 고치면 뭐가 나아지나

| 항목 | 현재 (build에 통합) | 별도 단계 추가 시 |
|---|---|---|
| 타입 오류 검출 | 됨 | 됨 |
| 실패 위치 표시 | "Build" 단계에서 실패 | "Type check" 단계에서 실패 |
| 실패까지 걸리는 시간 | 테스트(약 10초)를 다 돌린 뒤 | 테스트 전에 즉시 |
| 원인 파악 | 로그를 열어봐야 타입 오류인지 번들 오류인지 구분 | 단계 이름만 봐도 구분 |

정리하면 **기능 차이는 없고 피드백 속도와 가독성만 개선**됩니다. 급하지 않습니다.

### 적용 방법 (선택)

원하시면 아래 세 가지 중 편한 방법으로 직접 적용하시면 됩니다. 저는 권한이 없어 대신
푸시할 수 없습니다.

**방법 A — GitHub 웹 UI에서 직접 편집 (가장 간단)**

저장소 → `.github/workflows/ci.yml` → 연필 아이콘 → `Run tests` 단계 **위에** 아래 3줄 삽입:

```yaml
    - name: Type check
      run: npm run typecheck

```

**방법 B — 로컬에서 패치 적용**

저장소에 `docs/ci-typecheck.patch`를 만들어 두었습니다. 로컬에 클론한 뒤:

```bash
git checkout arena/01a00b33-project-generator
git pull
git apply docs/ci-typecheck.patch
git commit -am "ci: 타입 체크 단계 추가"
git push
```

**방법 C — Arena의 GitHub 연결에 workflows 권한 부여**

Arena 설정에서 GitHub 연결을 다시 인증하며 `workflows` 스코프를 허용하면, 이후 세션에서
제가 직접 수정할 수 있습니다.

### 참고: 원래 적용하려던 전체 내용

타입 체크 단계 외에 트리거 조건도 함께 손보려 했습니다. 현재 워크플로는
`branches: ["main"]`만 감시하므로 **지금 작업 중인 `arena/**` 브랜치에서는 CI가 아예 돌지
않습니다.** 이것도 방법 A/B로 함께 적용하시면 좋습니다.

```yaml
on:
  push:
    branches: ["main", "arena/**"]   # arena 브랜치도 CI 실행
  pull_request:                       # 모든 PR 대상 (main 한정 해제)
```

## 2. 인터프리터의 union은 "저장소 공유" 근사 구현

### 어떻게 구현되어 있나

`src/offline/interpreter.ts`의 `makeAggCell()`에서, union의 스칼라 멤버들은 **하나의
`Cell` 객체를 공유**하도록 만들어집니다.

```ts
/* union은 모든 스칼라 멤버가 같은 저장소를 공유한다 (근사 구현) */
const shared = def.kind === 'union' ? numCell(0) : null;
for (const m of def.members) {
  if (shared && m.dim === null && !m.aggTag) {
    fields.set(m.name, shared);   // 모든 스칼라 멤버가 같은 셀을 가리킴
    continue;
  }
  ...
}
```

실제 C의 union은 **같은 메모리 영역을 서로 다른 타입으로 재해석**합니다. 반면 이 구현은
**하나의 JavaScript number 값을 여러 이름으로 공유**합니다. "쓰기가 서로 보인다"는 성질은
같지만, **타입별 폭(width)과 바이트 레이아웃이 없습니다.**

### 실제 동작 차이 (측정 결과)

| # | 코드 | 실제 C (x86-64) | 현재 구현 | 일치 |
|---|---|---|---|---|
| 1 | `v.a=65;` → `v.a, v.b` | `65 65` | `65 65` | ✅ |
| 2 | `v.a=321;` → `v.a, v.b` | `321 65` | `321 321` | ❌ |
| 3 | `v.a=0; v.b=65;` → `v.a` | `65` | `65` | ✅ |
| 4 | `union {float f; int i;}` 재해석 | 큰 정수 | 근사 불가 | ❌ |
| 5 | `union {int w; char b[4];}` 오버레이 | `1` | `0` | ❌ |

> 선언은 `union U { int a; char b; };` 기준입니다.

**핵심은 2번입니다.** 실제 C에서 `int`에 321(`0x141`)을 넣고 `char`로 읽으면 하위 1바이트만
보여 65(`0x41`)가 나옵니다. 현재 구현은 폭 개념이 없어 321을 그대로 돌려줍니다.
값이 0~255 범위 안이면(1번) 우연히 일치하지만, 넘어가면 어긋납니다.

5번(배열 멤버 오버레이)과 4번(타입 재해석)은 아예 지원되지 않습니다. 배열 멤버는 공유
대상에서 제외되어 독립 저장소를 갖습니다.

참고로 **struct는 이 문제가 없습니다.** 멤버마다 독립 셀을 가지므로 실제 C와 동일하게
동작합니다(6번 케이스 검증 완료).

### 실제로 문제가 되나

지금 저장소에서는 **문제가 되지 않습니다.**

```
src/data/samples-a.ts : union 0건
src/data/samples-b.ts : union 0건
src/data/labs.ts      : union 0건
```

앱이 제공하는 C 샘플·실습 코드 어디에도 union이 없습니다. 영향 범위는 **사용자가 CodeLab
편집기에 union을 직접 타이핑해서 오프라인 실행하는 경우**로 한정됩니다.

또한 CodeLab에는 온라인 모드(Compiler Explorer / arm-none-eabi-gcc)가 있어서, 정확한
검증이 필요하면 그쪽으로 우회할 수 있습니다.

### 선택지

**A. 현행 유지 (권장)**

union 미사용 + 온라인 모드 대안 존재 + 학습용 데모라는 점을 고려하면 합리적입니다.
다만 사용자가 조용히 틀린 값을 믿는 상황은 피하는 게 좋으므로, 최소한 **union 선언 시
"오프라인 엔진의 union은 근사 구현입니다. 정확한 바이트 레이아웃은 온라인 모드로
검증하세요"라는 경고를 출력**하는 것을 함께 제안드립니다. 작업량 30분 수준입니다.

**B. 타입별 폭 마스킹 (중간)**

멤버 타입을 기억해뒀다가 읽을 때 마스킹합니다. `char`면 `& 0xff`, `short`면 `& 0xffff` 식입니다.
위 표의 2번이 해결되어 정수 계열 union은 대부분 맞게 동작합니다.
4번(float 재해석)과 5번(배열 오버레이)은 여전히 불가합니다. 작업량 2~3시간.

**C. 실제 바이트 버퍼 (완전)**

union 인스턴스를 `ArrayBuffer`로 만들고 멤버별 오프셋/타입에 따라 `DataView`로 읽고 씁니다.
4번·5번을 포함해 전부 정확해집니다. 다만 이 구조를 제대로 하려면 struct의 메모리
레이아웃(정렬·패딩)도 같이 바이트 기반으로 바꿔야 해서, 인터프리터 런타임의
값 표현(`Cell`)을 광범위하게 수정해야 합니다. 작업량 1~2일, 회귀 위험 있음.

### 참고: 이번에 함께 고친 것

이 검증 과정에서 별개의 버그를 발견해 수정했습니다. `float`가 `TYPE_WORDS` 목록에서 누락되어
`float x = 2.5;`가 `타입 키워드 필요` 오류로 실패하고 있었습니다. `volatile`, `extern`,
`register`, `inline`도 함께 누락되어 있었습니다.

```ts
// 수정 전
'int', 'double', 'char', 'void', 'long', 'short', 'unsigned', 'signed', 'static', 'const',

// 수정 후
'int', 'double', 'float', 'char', 'void', 'long', 'short', 'unsigned', 'signed',
'static', 'const', 'volatile', 'extern', 'register', 'inline',
```

`float`는 내부적으로 `double`로 처리합니다(JavaScript number가 배정밀도이므로 자연스러운
매핑입니다. 단정밀도 반올림 오차까지 재현하지는 않습니다).
회귀 테스트를 추가했습니다 — `float / volatile 타입 키워드 지원`.
